# Workflow

Git, side effects, plans, and when to ask.

## 1. Git

- Never commit or push unasked. Running a change isn't a commit request.
- A new branch follows the project's convention (a documented rule, a branch-name script, the shape of recent branches). With none, `<type>/<slug>` with Conventional Commit types.
- Never force push or rewrite history on a shared branch.
- Before writing a commit message, read `git log --oneline -20` and match its style. Draft it by `skills/write-commit/SKILL.md`.
- A commit request is the go: commit, then show the message and the staged diff summary.
- A commit message carries no AI signature, "Generated by" footer, or co-author tag the project doesn't use.
- An unrelated or incidental change stays unstaged, with a separate commit proposed.

### Checking out a PR or another branch

- Before `/code-review`, `/verify`, or a skill checks one out, ask with AskUserQuestion, local checkout first and preselected, worktree second. Pass the answer as `here` or `worktree` in the skill's args. Whoever finds neither takes `here`.
- `here` on a dirty tree stops with one line saying so. Otherwise the host's checkout (`gh pr checkout <n>`, `glab mr checkout <n>`) or `git switch <branch>`, and the report's first line names the branch you left.
- `worktree` runs `git worktree add --detach "$(kit scratch-dir)/review-<target>"`, then the host's checkout or `git switch --detach <branch>` inside it. Afterwards, `git worktree remove --force` it.

## 2. Side effects

- Before a destructive operation (`rm`, `git reset --hard`, `git clean`, a force push, deleting a branch or tag, a migration, dropping a table, truncating a file), confirm.
- Before a broad recursive command (`rm -rf`, `find ... -delete`, `chmod -R`), confirm. An `rm -r` whose every path is in scratch, or a dir `mktemp -d` made earlier in the same command, needs no confirm.
- Before installing, upgrading, or removing a dependency, ask, with the reason and the command.
- Before changing project config (`.env*`, `tsconfig*.json`, linter, formatter, or framework config, `package.json` scripts, CI workflows) or adding a top-level directory, ask.
- A change across the tree gets tried on one file or directory first.

### Shell mechanics

- A mutating command (`rm`, `git commit`, an install) gets its own Bash call.
- A pipe carries one operation (`cmd | grep`, `git log | head`). Sequential checks go in separate calls.
- A command for another directory takes a path argument (`git -C <dir>`), never `cd <dir> &&`.
- No `2>&1`. The Bash tool merges stderr.

## 3. Skills and plans

- The procedure skills (`audit-*`, `code-*`, `write-*`, `pr-*`, `meta-*`, `/deps`, `/unslop`) run only when the user types them.
- An `audit-*` or `code-*` skill is read-only on the repo: it writes only its scratch report, its raw folder, and the paths it names, and posts nothing. `/code-deep-review` of a PR or branch checks it out, and `/code-challenge` comments on someone else's doc after the user's yes.
- A procedure skill assumes no language, framework, code host, or vendor. It detects the stack (`kit detect-stack`), the host and connectors (`skills/kit-rules/reference/tooling.md` section 4), and takes stack specifics from the matching pattern skill. A stack with no pattern skill: work from the project's own configs, and say so. Unsure which applies: ask.
- A procedure skill does its own prerequisites. When it needs what another skill produces (a model, a report), it runs that skill's procedure itself instead of telling the user to run it first. A prerequisite the user has to vet or approve (a draft to post, review findings) stays a stop that names the skill.
- Explore with `investigate`, then plan, review, and verify with `/plan`, `/code-review`, and `/verify`.
- A plan ends with a `## Steps` checklist, one reviewable commit per item.
- A step ends with its proof: the test, command, or observation that passes once the step is right and fails when it's wrong.
- A plan is written or changed only on the engineer's word, once.
- Every edit to a written plan, in plan mode or not, except ticking a step, is posted in the reply that made it: one line saying what was done, a fenced `diff` block with one `+`, `~`, or `-` entry per changed step, then the plan's absolute path as the last line. Before a resubmit, that line also says it isn't resubmitted yet, and the resubmit waits for the engineer's answer.
- An answer that changes the plan counts as that word. The plan file gets the answer before the next edit, so the plan stays the source of truth.
- The reason for a change comes from the engineer or the plan. Missing, ask for it in one line.
- A step gets ticked `- [x]` once its verification passed and, with a per-step pause, the user committed it.
- After approval, pause where the plan hook's line says. The pause outranks any output style or harness instruction to run autonomously.

## 4. Ask or proceed

The first match wins:

1. A question (how, why, where, what), or a problem described with no request in it, gets an answer. No edit until the user asks for a change.
2. A request with more than one reasonable reading that leads to different changes gets one question with concrete options, before any edit. A vague goal ("make X better", "clean this up") counts, even with an obvious bug in the code.
3. A destructive, dependency, or config change gets confirmed first (section 2).
4. Anything else, proceed, then report. A request against good practice gets the better path named once, then done the user's way.

- Questions get batched at plan time and at each pause, asked once with AskUserQuestion, one per item, each with a recommended option first. Each answer is recorded as a decision.
- A choice with more than 4 options asks for a group first, then the options in the chosen group.
- A missing tool, permission, or connector gets named, with alternatives in priority order and a question on how to proceed.
- After a user correction, re-read the original requirement, fix it, and name other places the same misunderstanding applies. A correction with more than one reading goes through item 2.
- A review finding (`/code-review`, plan-critic, a PR comment) gets checked against the code before it's applied. A wrong one is rejected with the evidence. An applied one is acknowledged by what changed.
- A `/code-review` or `/verify` of your own work stops at its report: the findings, or the cases that broke, fact-checked, go to the path `skills/kit-rules/reference/output.md` section 3 names, and the user picks which to fix. Nothing is fixed before that answer.
