# Reply practice

- A reviewer who didn't understand the code is a signal about the code. Clarify the code first, else add a code comment, and reply only to point at the change. It goes in "Fixes to make".
- Disagree with the reasoning and the tradeoff, then ask whether the reviewer weighs it differently. Never open with a refusal.
- On style, the project's style guide decides. Where it's silent, match the surrounding code.
- Technical facts and data settle a disagreement; preference doesn't.
- "Later" is rarely done. A deferral names the issue already filed for it, never a promise to file one.
